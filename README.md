# CAIMP — The DevOps Engineer Your Small Team Doesn't Have

CAIMP is a self-hosted AI monitoring platform that doesn't just tell you *something is broken* — it tells you **why it broke and what to do about it**. Built for startup developers who manage their own servers without a dedicated DevOps engineer.

> *"Okay, I know something is broken. Now tell me WHY."*
>
> That 30-minute investigation after every alert? That's what CAIMP replaces.

---

## What It Does

The default dashboard opens to a direct answer — not a wall of graphs:

```
┌─────────────────────────────────────────────────────────────┐
│  ⚠  2 Issues Need Attention   —   4 of 5 servers online     │
├─────────────────────────────────────────────────────────────┤
│  POTENTIAL ISSUES                                           │
│  • db-primary: Memory will hit critical in ~5 hours         │
│  • web-01: 8 unusual readings in the last 24 hours          │
├─────────────────────────────────────────────────────────────┤
│  RECOMMENDED ACTIONS                                        │
│  1. Investigate memory on db-primary immediately            │
│  2. Check the anomaly log for web-01                        │
├─────────────────────────────────────────────────────────────┤
│  [ View detailed metrics → /metrics ]                       │
└─────────────────────────────────────────────────────────────┘
```

**Core capabilities:**

- **Answers-first dashboard** — the home page shows status, issues, and actions. Graphs are one click away at `/metrics`.
- **Change correlation** — when an anomaly fires, CAIMP automatically searches what changed on that server in the 30 minutes before it (deployments, Docker pulls, config edits, package installs, SSH logins, cron jobs) and scores each change by likelihood of being the cause.
- **AI root-cause analysis** — every anomaly gets a plain-English explanation with a specific action step, generated by a local LLM (no cloud required).
- **24-hour forecasting** — Holt-Winters time-series prediction tells you when CPU/memory/disk will hit critical, with an AI narrative.
- **Alert deduplication** — the same anomaly firing repeatedly within 15 minutes is suppressed; 3+ different metrics spiking on the same server within 60 seconds are flagged as a burst.
- **Live push updates** — the dashboard refreshes the moment something is detected via WebSocket, no polling.
- **PDF health reports** — structured, plain-language PDF reports readable by non-technical stakeholders.
- **Runbooks** — write fix guides once; they are embedded into the vector DB and automatically injected as context when the AI explains a matching anomaly.
- **AI chat** — ask questions about any server or incident in natural language via a floating chat panel.
- **Optional Splunk integration** — enterprise metric indexing, MLTK anomaly detection, and a secondary AI pipeline.

## How Everything Works — Pipeline by Pipeline

### 1. Metric Collection

The `caimp-agent` runs on each monitored server. Every 15 seconds it reads CPU, memory, and disk usage and sends them via **OTLP/HTTP** to the Telemetry Writer (:4318). The Telemetry Writer batches the data and writes it to the `metrics` TimescaleDB hypertable.

If you have Splunk, the agent can also send to the **Splunk HEC Bridge** (:4317), which translates OTLP to Splunk HEC format and additionally caches live metric values in Redis (90-second TTL).

### 2. Anomaly Detection

As metrics arrive, the Telemetry Writer runs three detectors in parallel:

| Detector | Trigger |
|----------|---------|
| **Threshold** | CPU > 90%, RAM > 90%, Disk > 85% |
| **Z-Score** | Reading > 3 standard deviations from historical mean |
| **Rate of Change** | Metric jumped > 20% in a single interval |

On detection: saves `anomaly_events` row → publishes `anomaly.detected.{org_id}.{severity}` to NATS JetStream.

### 3. Change Tracking

The `caimp-agent` runs four background reporters alongside metric collection:

| Reporter | Watches |
|----------|---------|
| `DockerEventsReporter` | `docker events` stream — image pulls, container restarts |
| `PackageWatcher` | `/var/log/dpkg.log`, `yum.log`, `apt/history.log` — installs/removals |
| `AuthWatcher` | `/var/log/auth.log` — SSH login and logout |
| `CronWatcher` | `/var/log/syslog` — CRON CMD entries |

All events POST to the **Change Tracker** (:8011), which also receives GitHub/GitLab webhooks for deployments and CI/CD events. Every change is saved to the `change_events` TimescaleDB hypertable and published to `change.detected.{org_id}` on NATS.

### 4. AI Explanation

The **AI Worker** subscribes to `anomaly.detected.>`. For each anomaly:

1. Fetches last 30 min of metric readings from PostgreSQL
2. Queries `rag_documents` and `runbooks` via **pgvector** cosine similarity for similar past incidents
3. Builds a plain-English prompt (targeting non-DevOps developers) and calls **Ollama**
4. The LLM returns `{explanation, root_cause, recommended_action, confidence}` as JSON
5. Saves to `ai_explanations` → publishes `ai.explanation.ready.>` to NATS → WS Gateway pushes to browser

### 5. Change Correlation — "What changed before this broke?"

The **Correlation Engine** also subscribes to `anomaly.detected.>`. For each anomaly it:

1. Queries `change_events` for the 30-minute window before the anomaly on the same server
2. Scores each candidate change:
   - **Temporal score**: `exp(−0.1 × minutes_before)` — changes right before the anomaly score highest
   - **Type weight**: deployment (1.0), config (0.9), package (0.8), Docker pull (0.75), restart (0.7), cron (0.5), SSH (0.3)
3. Sends the top 3 ranked changes + anomaly context to Ollama with a plain-language prompt
4. Saves `{likely_cause, confidence, correlated_changes, narrative, recommended_actions}` to `root_cause_analyses`
5. Publishes `rootcause.ready.{org_id}` → WS Gateway → browser

### 6. Alert Deduplication

Before any anomaly is persisted, the **Alert Engine** checks a Redis NX key `dedup:{org_id}:{server_id}:{metric}:{detector}` with a 15-minute TTL. If the key exists, the anomaly is suppressed (same problem already open). A separate burst tracker flags when 3+ different metrics fire on the same server within 60 seconds.

### 7. 24-Hour Forecasting

The **Forecast Engine** runs every 30 minutes:

1. Fetches the last 6 hours of CPU/memory/disk data per server
2. Runs **Holt-Winters double exponential smoothing** (pure NumPy, no ML dependency)
3. Generates 24 hourly prediction points with ±1.28σ confidence intervals
4. Calls Ollama to write a plain-English narrative
5. Calculates `time_to_critical` — hours until the metric is predicted to exceed 90%
6. Saves to `server_forecasts`; publishes `forecast.critical.>` if breach is within 6 hours

A second evaluate loop (every 60 min) scores past forecasts against actual values and stores the accuracy so the LLM can calibrate confidence in future narratives.

### 8. Answers-First Dashboard

`GET /api/v1/dashboard/summary` aggregates across all the above and returns:

- **`overall_status`**: `healthy` / `warning` / `critical`
- **`potential_issues`**: prioritised list from forecasts at risk, anomaly clusters, root-cause analyses, offline servers
- **`recommended_actions`**: ordered numbered fix steps with plain-English reasons
- **`servers`**: mini health summary per server

The React dashboard at `/` displays this as a single-screen status view. The old graph-first dashboard is at `/metrics`.

### 9. Live Updates (NATS → WebSocket → Browser)

The **WS Gateway** subscribes to all event subjects on NATS and fans them out over WebSocket to every connected browser tab. No polling — the dashboard auto-refreshes within 2–3 seconds of any anomaly, AI completion, or root-cause result.

### 10. Splunk Integration (Optional)

```
Splunk MLTK detects anomaly
        │  savedsearch fires caimp_webhook alert action
        ▼
  AI Orchestrator :8010
        ├─ 1. Queries Splunk mstats for metric context
        ├─ 2. RAG lookup in pgvector
        ├─ 3. Calls Ollama (or Anthropic Claude for critical alerts)
        ├─ 4. Validates JSON output schema
        ├─ 5. Saves to splunk_ai_explanations
        ├─ 6. Caches in Redis (24h TTL)
        ├─ 7. Writes explanation back to Splunk caimp_ai index
        └─ 8. Publishes to NATS → WS Gateway → browser
```

## Running CAIMP

### Requirements

| | Minimum | Recommended |
|--|---------|-------------|
| RAM | 6 GB | 16 GB |
| CPU | 4 cores | 8+ cores |
| Disk | 20 GB | 50 GB |
| OS | Linux / macOS / Windows | Linux |
| Docker | 24+ | latest |
| Docker Compose | v2.20+ | latest |

> **4 GB machine?** See [Low-RAM mode](#low-ram-mode-4-gb) below.

### Step 1 — Get the code

```bash
git clone https://github.com/your-org/caimp.git
cd caimp
```

### Step 2 — Configure

```bash
cp .env.example .env
```

Edit `.env` — these are required:

```bash
POSTGRES_PASSWORD=your_strong_password
REDIS_PASSWORD=your_strong_redis_password
NATS_PASSWORD=your_strong_nats_password
JWT_SECRET=<output of: openssl rand -hex 64>
CA_KEY_PASSPHRASE=your_ca_passphrase
GRAFANA_ADMIN_PASSWORD=your_grafana_password
```

Optional (leave blank to disable Splunk integration):

```bash
SPLUNK_HOST=
SPLUNK_PASSWORD=
SPLUNK_HEC_URL=
SPLUNK_HEC_TOKEN_METRICS=
```

Optional (for GitHub webhook signature verification):

```bash
GITHUB_WEBHOOK_SECRET=your_webhook_secret
```

### Step 3 — Start

```bash
make up
# or: docker compose up -d
```

First run builds all images (~3–5 min) and runs database migrations automatically.

```bash
make ps    # all containers should show "healthy" or "running"
```

### Step 4 — Pull AI models (first run only)

```bash
make pull-models
# Pulls: llama3.1:8b-instruct-q4_K_M (~5 GB) + nomic-embed-text (~270 MB)
```

### Step 5 — Open the dashboard

Go to **http://localhost** in your browser.

```
Email:    admin@caimp.local
Password: Admin1234!
```

### Step 6 — Load demo data (optional)

```powershell
# Windows
.\scripts\seed_demo.ps1
```
```bash
# Linux / macOS
docker compose exec postgres psql -U caimp -d caimp < scripts/seed_demo.sql
```

Populates 5 servers, 7 days of metrics, anomaly events, AI explanations, forecasts, and runbooks.

### Step 7 — Monitor a real server

**1. Generate an enrollment token:**

```bash
curl -s -X POST http://your-caimp-host:8001/admin/servers/enroll \
  -H "Authorization: Bearer YOUR_JWT" \
  -H "Content-Type: application/json" \
  -d '{"server_name": "my-server", "hostname": "my-server.example.com"}' \
  | jq '.enrollment_token'
```

**2. Install the agent on the target Linux server:**

```bash
curl -fsSL http://your-caimp-host/install.sh | bash -s -- \
  --token YOUR_ENROLLMENT_TOKEN \
  --url http://your-caimp-host
```

Or manually:

```bash
cd /opt/caimp-agent/services/agent
pip3 install -r requirements.txt
python3 main.py --enroll YOUR_ENROLLMENT_TOKEN
```

**3. Run as a system service:**

```bash
cp services/agent/caimp-agent.service /etc/systemd/system/
systemctl enable --now caimp-agent
```

The server appears on the dashboard within 30 seconds. The agent automatically starts reporting Docker events, package installs, SSH logins, and cron jobs to the change tracker — these feed the correlation engine.

### Step 8 — Connect GitHub/GitLab webhooks (optional)

To correlate deployments with incidents, add a webhook to your repository:

- **URL:** `http://your-caimp-host/api/changes/webhooks/github?org_id=YOUR_ORG_ID`
- **Events:** Push, Deployment, Workflow run
- **Secret:** value of `GITHUB_WEBHOOK_SECRET` in your `.env`

For GitLab: `/api/changes/webhooks/gitlab?org_id=YOUR_ORG_ID`

## Database Schema

| Table | Purpose |
|-------|---------|

## Troubleshooting

**A container is unhealthy or not starting:**
```bash
docker compose ps
make logs-postgres    # postgres must be healthy first — everything depends on it
make logs-migrate     # check all 14 migrations ran successfully
```

**Dashboard shows no issues but I know something is wrong:**
```bash
# Confirm the agent is sending metrics
journalctl -u caimp-agent -f

# Check anomaly detection thresholds — they may need lowering
# Set in .env: TW_CPU_THRESHOLD_PCT=80 and rebuild telemetry-writer
```

**AI explanations not appearing:**
```bash
make logs-ai-worker
make logs-ollama
docker compose exec ollama ollama list    # verify models are pulled
```

**Root-cause analyses not appearing:**
```bash
make logs-correlation-engine
# Note: correlation engine only fires when change_events exist.
# With no webhook or agent reporters, the table will be empty.
```

**Change events not being recorded:**
```bash
make logs-change-tracker
# Check that CAIMP_SERVER_ID is set in the agent's environment
# Check that the agent can reach http://your-caimp-host/api/changes/ingest
```

**Forecasts not updating:**
```bash
make logs-forecast-engine
# Forecasts run every 30 min — wait or force a restart:
docker compose restart forecast-engine
```

**Disk growing fast:**
```bash
make psql
# Check database size:
SELECT pg_size_pretty(pg_database_size('caimp'));
# TimescaleDB auto-compresses old data. For manual cleanup:
# metrics table: hypertable retention set to 90 days by default
# change_events: 7-day retention in NATS; DB rows persist until manual cleanup
```

## Splunk Integration Setup

1. Copy app config to your Splunk server:
   ```bash
   cp -r splunk/ $SPLUNK_HOME/etc/apps/caimp/
   ```
2. Create three HEC tokens: **Settings → Data Inputs → HTTP Event Collector** (metrics, logs, AI writeback).
3. Set in `.env` and restart:
   ```bash
   SPLUNK_HEC_URL=https://your-splunk:8088
   SPLUNK_HEC_TOKEN_METRICS=your-token
   SPLUNK_HOST=your-splunk:8089
   SPLUNK_PASSWORD=your-splunk-password
   ```

Full guide including MLTK training searches, rollup indexes, and KV Store configuration: `splunk/README.md`.

## Security

- All inter-service traffic stays inside the `caimp_net` Docker bridge — nothing is reachable from outside except the declared ports
- Monitoring agents use **mTLS** — certificates issued by an internal CA stored in PostgreSQL; enrollment tokens are one-time use
- JWT access tokens expire in 15 minutes; refresh tokens in 7 days; revoked tokens are blacklisted in Redis
- Splunk passwords stored AES-256-GCM encrypted in `org_config`
- `.env` is gitignored — never commit it
- For production TLS: place a certificate in `infra/nginx/certs/` and set `NGINX_HTTPS_PORT=443`
